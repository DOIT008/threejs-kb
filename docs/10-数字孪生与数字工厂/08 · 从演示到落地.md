# 从演示到落地

前面七篇做出来的东西，放在展会上演示很漂亮。但真要把它装进工厂、7×24 小时跑起来，你会遇到一堆"代码之外"的问题：设备协议对不上、模型和现场差了半米、老浏览器白屏、老板问"这玩意儿多少钱多久能上线"……这篇不讲渲染技巧，专讲**工程落地**。

## 一、从 demo 到产品，差的不只是代码

先把话说透：**演示项目和上线项目的差距，80% 不在 Three.js，而在数据、运维和人的因素。**

| 维度 | 演示 demo | 上线产品 |
|---|---|---|
| 数据 | `setInterval` 造假 | 真实设备协议接入、断线重连 |
| 用户 | 你自己 | 操作员、工程师、访客，权限各不同 |
| 设备 | 6 台方块 | 几百台、上千测点 |
| 运行时间 | 演示 10 分钟 | 7×24 小时不停机 |
| 出问题 | 刷新页面 | 要有监控、告警、回滚 |
| 验收 | "看着挺炫" | 有量化指标和签字 |

::: tip 大白话时间

demo 像**样板间**——灯光打得漂亮，但没人真住。落地项目像**真房子**——水电煤气、物业、维修、邻里关系全都要管。Three.js 只负责"样板间的装修"，真正让它能住人的，是数据管线和工程规范。

:::

## 二、数据接入协议：OPC UA / MQTT / Modbus 是啥

这是落地第一关。设备不会说 HTTP，它们说自己的"方言"。三种最常见的：

| 协议 | 用在哪 | 特点 | 大白话 |
|---|---|---|---|
| **OPC UA** | 现代工业设备、PLC | 跨平台、安全、带信息模型，但偏重 | "工业界的普通话"，正规但学起来费劲 |
| **MQTT** | 物联网上云、设备到平台 | 轻量、发布/订阅、弱网友好 | "对讲机"，谁订阅谁听，省流量 |
| **Modbus** | 老设备、仪表 | 简单古老，走串口/网口，几乎无安全机制 | "老一辈的方言"，设备还在但很脆弱 |
| WebSocket | 后端到浏览器 | 全双工、浏览器原生 | 前端拿到数据的"最后一公里" |

::: info 信息

它们不是竞争关系，而是**分层协作**：老设备说 Modbus，边缘网关把它翻译成 MQTT；新设备直接说 OPC UA，网关也转成 MQTT；后端订阅 MQTT 收数据，处理后用 **WebSocket 推给浏览器**。浏览器不直接跟设备对话——这样安全、好扩展。

:::

**典型数据链路：**

```text
PLC / 传感器 / 设备
      │ Modbus / OPC UA / 私有协议
      ▼
边缘网关（协议转换 + 缓存 + 断网续传）
      │ MQTT（发布）
      ▼
MQTT Broker（消息中枢）
      │ 订阅
      ▼
后端服务（清洗 → 聚合 → 存时序库）
      │ WebSocket
      ▼
前端（Pinia → Three.js 场景）
```

::: warning 注意

**千万别让浏览器直连设备。** 浏览器直连 Modbus/OPC UA 既要装插件、又有跨域和安全问题，设备还暴露在公网。必须经过网关和后端这一层，前端只跟自己的后端说 WebSocket。

:::

## 三、后端架构：数据怎么从设备到浏览器

后端承担四件事，缺一不可：

| 模块 | 职责 | 常见选型 |
|---|---|---|
| 接入层 | 收设备数据、协议转换 | EMQX / Mosquitto（MQTT Broker），自研网关 |
| 处理层 | 清洗、去重、聚合、算指标 | Node.js / Java / Go 服务 |
| 存储层 | 存历史数据，供回放分析 | InfluxDB / TDengine / TimescaleDB（时序库） |
| 推送层 | 把实时数据推给前端 | WebSocket（Socket.IO / ws） |

::: tip 大白话时间

时序数据库和普通数据库的区别：**普通数据库像 Excel 表格，时序库像心电图纸**——它专门存"某个时间点某个测点的值"，按时间顺序一条条记，查"昨天下午 3 点温度曲线"特别快。设备数据天然就是时间序列，用对工具省一半劲。

:::

## 四、与真实设备联调的坑

这部分是"血泪经验"，对照表格提前避坑：

| 坑 | 现象 | 对策 |
|---|---|---|
| 数据字典不一致 | 前端拿到 `status: 1`，不知道啥意思 | 提前定好字段/枚举的**数据字典**，网关层做归一化 |
| 时间戳乱 | 曲线错乱、差 8 小时 | 统一用 **UTC 毫秒时间戳**，别传本地时间字符串 |
| 单位不统一 | 温度 68 其实是 68°F | 数据字典里写死单位，网关统一换算 |
| 高频数据压垮前端 | 页面越用越卡 | 后端按 100~500ms 聚合，前端再节流 |
| 中文乱码 | 设备名变问号 | 全链路 UTF-8，数据库、消息、接口都检查 |
| 断网后界面"冻住" | 设备显示故障前的绿 | **心跳超时**标离线 + 自动重连 + 断线提示 |
| 坐标对不上 | 模型和现场差半米 | 基准点 + 实测校准（见下一节） |
| 反向控制误操作 | 有人手滑点了"停机" | 二次确认 + 权限控制 + 审计日志 |
| 老机器白屏 | 某些工控机打不开 | 启动时检测 WebGL2，给降级提示 |
| 控制指令无反馈 | 点了启动，不知道成没成 | 做成"请求-确认"闭环，回执后再改 UI |

::: danger 警告

**反向控制（从 3D 界面控制真实设备）是最高危功能。** 必须同时做到：操作权限校验、二次弹窗确认、操作审计留痕、失败可回滚。工业现场一次误停机可能造成真实的经济损失甚至安全风险。能不做就先不做；要做就把上面四条当铁律。

:::

## 五、坐标与真实厂区对齐

demo 里设备坐标是你随口写的。真实项目里，**模型必须和现场一一对应**，否则监控就失去意义。

**对齐四步法：**

1. **拿图纸**：向甲方要厂区 CAD 图或设备布置图，确认坐标系和单位（多半是毫米）；
2. **定原点**：选一个固定参照物（比如车间西南角柱）作为 `(0, 0, 0)`；
3. **做转换**：CAD 常用 Z 轴朝上，Three.js 是 Y 轴朝上，且单位要换算；
4. **现场校准**：拿激光测距仪实测 3~5 个基准点，比对模型坐标，误差大就调变换参数。

```js
// CAD 常用 Z-up、单位毫米；Three.js 是 Y-up、单位米
// 把 CAD 的 (x, y, z) 转成 Three 的 (x, y, z)
function cadToThree([x, y, z]) {
  return [
    x / 1000,   // CAD 的 X → Three 的 X，毫米转米
    z / 1000,   // CAD 的 Z（高） → Three 的 Y（高）
    -y / 1000   // CAD 的 Y → Three 的 Z（注意方向取反）
  ]
}

// 如果整体还差一点，套一个统一偏移/旋转来微调
const OFFSET = { x: 0.3, z: -0.2 }; // 现场校准出来的修正值
function toScene(cadPoint) {
  const [x, y, z] = cadToThree(cadPoint);
  return [x + OFFSET.x, y, z + OFFSET.z];
}
```

::: tip 大白话时间

坐标对齐就像**把地图铺到地上**：图纸是地图，车间是地。你得先找到"地图上的哪个点对应地上的哪根柱子"（定原点），再保证地图比例是对的（单位换算），最后用尺子量几个点验证（现场校准）。**别相信图纸上的理论值，一定到现场量。** 图纸和现实差个几十厘米是常事。

:::

## 六、模型轻量化：别把几 GB 的模型塞进浏览器

工业模型通常来自 SolidWorks / Revit / BIM，动辄几百 MB 甚至几个 GB。**浏览器扛不住，必须先减肥。**

| 手段 | 做法 | 效果 |
|---|---|---|
| 减面 | Blender 里 Decimate，删掉看不见的内部零件 | 面数降 90% 很常见 |
| 格式转换 | 转 glTF/GLB，别用 OBJ/FBX | 加载快、结构紧凑 |
| Draco 压缩 | `gltf-transform optimize` 或 `DRACOLoader` | 几何体体积大幅缩小 |
| 纹理压缩 | 转 KTX2 / WebP，合并图集 | 显存和带宽双降 |
| 实例化 | 相同设备用 `InstancedMesh` | draw call 从几百降到几个 |
| LOD | 远处用简模，近处用精模 | 远处省性能 |
| 分块加载 | 按车间/楼层分批加载 | 首屏只加载当前区域 |

::: info 信息

一个经验目标：**首屏资源控制在 20~50MB 以内，draw call 控制在 1000 以内**。超了这个量，普通工控机（集成显卡）会明显卡顿。上线前务必在**客户实际使用的机器**上测，别只在自己的高配开发机上跑。

:::

```js
// 用 DRACOLoader 加载压缩过的 GLB（r187 写法）
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { DRACOLoader } from 'three/addons/loaders/DRACOLoader.js';

const draco = new DRACOLoader();
draco.setDecoderPath('https://www.gstatic.com/draco/versioned/decoders/1.5.7/');
const loader = new GLTFLoader();
loader.setDRACOLoader(draco);
loader.load('/models/workshop.glb', gltf => {
  scene.add(gltf.scene);
});
```

::: warning 注意

_decoder 路径别乱填_，要和压缩 GLB 时用的 Draco 版本匹配，否则加载报错。离线部署的项目要把 decoder 文件**放到本地**并改成本地路径，不能依赖外网 CDN。

:::

## 七、权限与多租户

一个系统往往给多个车间、多个客户用，必须做隔离。

### 权限（RBAC 角色）

| 角色 | 能看什么 | 能做什么 |
|---|---|---|
| 访客 | 只读总览 | 不能点控制按钮 |
| 操作员 | 本工段设备 | 查看、确认报警 |
| 工程师 | 全部设备 | 查看、复位、参数调整 |
| 管理员 | 全部 + 系统配置 | 用户管理、权限分配、反向控制 |

### 多租户隔离

- 每条设备数据带 `tenantId` / `factoryId`，**后端查询强制带上租户过滤**，不能只靠前端藏；
- WebSocket 连接携带 token，后端校验该连接**只能订阅自己租户的数据**；
- 静态资源、模型文件也按租户分目录，避免 A 客户看到 B 客户的厂区。

::: danger 警告

**权限校验必须在后端做，前端的隐藏按钮只是体验优化，不是安全边界。** 黑客可以直接调接口。任何"越权能看到/控制别的租户设备"的漏洞都是重大事故。

:::

## 八、移动端适配

现场人员常常用手机/平板看，不能只在电脑上好看。

| 方面 | 做法 |
|---|---|
| 布局 | 看板折叠成抽屉/Tab，3D 场景占主屏 |
| 触控 | `OrbitControls` 原生支持触摸；点击拾取的位移阈值要放大到 10px（手指没有鼠标准） |
| 性能降级 | 移动端 `pixelRatio` 封顶 1.5、关阴影、减粒子、降模型精度 |
| 横竖屏 | 复杂场景提示"请横屏查看" |
| 字体 | 看板数字放大，适配弱光车间环境 |

::: tip 大白话时间

工控机往往是**十年前的集成显卡**，手机反而比它新。所以"移动端适配"不只是屏幕变小，更是**给性能弱的设备留后路**：检测到帧率过低就自动关阴影、降特效。宁可画面朴素点，也别卡到没法用。

:::

## 九、验收指标

上线要有量化标准，别凭"看着挺好"验收：

| 指标 | 参考目标 | 怎么测 |
|---|---|---|
| 数据刷新延迟 | ≤ 2 秒 | 对比 PLC 时间戳和界面显示时间 |
| 场景帧率 | PC ≥ 30fps，移动端 ≥ 20fps | Chrome Performance 面板 |
| 首屏加载时间 | ≤ 5 秒（4G/厂区网） | Lighthouse / 实际抓包 |
| 设备状态准确率 | 100% | 抽 20 台设备对照现场 |
| 拾取命中率 | ≥ 95% | 随机点 100 次统计 |
| 连续运行稳定性 | 72 小时无崩溃、无内存泄漏 | 长稳测试 + 内存监控 |
| 断线恢复 | 30 秒内自动重连并补数据 | 人为断网测试 |

## 十、成本与周期估算表

::: info 信息

下面是**粗略参考区间**，实际价格受地区、模型精度、设备数量、协议复杂度、是否要反向控制等因素影响很大，仅供立项时估个量级，不作为报价。

:::

| 项目类型 | 设备规模 | 参考周期 | 团队配置 | 成本量级 |
|---|---|---|---|---|
| 概念演示 demo | 10 台以内，假数据 | 2~4 周 | 1~2 人 | 数万元 |
| 单车间试点 | 30~80 台，接真实数据 | 2~4 个月 | 4~6 人 | 数十万元 |
| 全厂推广 | 数百台，多车间 | 6~12 个月 | 8~15 人 | 数百万元 |
| 集团多租户平台 | 多厂区 + 权限 + 移动端 | 12 个月以上 | 15 人以上 | 千万元级 |

成本大头通常不是 Three.js 开发，而是：**设备协议对接、3D 模型整理、现场实施与校准、后端与运维**。这四项加起来往往占 70% 以上。

## 十一、上线检查清单

上线前照着逐条打勾：

- [ ] 所有设备数据接入真实协议，数据字典双方签字确认
- [ ] 时间戳统一 UTC 毫秒，单位统一并验证
- [ ] 模型完成轻量化，在**客户实际机器**上帧率达标
- [ ] 坐标与现场实测校准，误差在可接受范围
- [ ] 心跳超时 → 设备自动标离线，断线能自动重连
- [ ] 反向控制有权限校验 + 二次确认 + 审计日志
- [ ] 权限按角色隔离，后端做了越权校验
- [ ] 多租户数据隔离验证（A 租户看不到 B 租户）
- [ ] 移动端布局与性能降级验证
- [ ] WebGL2 检测 + 不支持时的降级提示
- [ ] 组件销毁时 WebSocket 关闭、渲染循环停止、资源 dispose
- [ ] 72 小时长稳测试通过，无内存泄漏
- [ ] 监控告警接入（接口异常、连接断开、帧率过低）
- [ ] 有回滚方案，出问题能切回旧版本
- [ ] 运维文档、数据字典、验收报告齐全
